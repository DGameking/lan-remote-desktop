# 14｜LanDesk v1.4.0 全面审校报告

> 日期：2026-11-22｜对象：v1.4.0（HEAD `324bc28`，工作区干净）｜方法：五个独立维度并行审校 + team-lead 独立交叉核实
> 目的：回答用户的核心问题——**"这是不是一个功能完整可用且好用的产品，而不是半成品？"**
> 口径：以项目自己冻结的 `docs/02c-最终验收标准.md`（REQ-001~012）为准绳，不降低标准、不因"测试全绿"而放行。

---

## 〇、一句话结论

**不是纯白板，但远称不上"完整可用且好用"。**

核心链路（发现 → 选协议 → 调起外部客户端 → 凭据免密）是**真实实现且可用的**，这不是半成品的骨架；但按项目自己定的 P0 验收标准，**REQ-009 / REQ-010 / REQ-011 三项存在零实现或结果失真**，加上一个随时间恶化的**安全 P0（Electron 已 EOL）**和一个直接造成"白板感"的 **UX 断链**。当前版本应定性为：

> **"核心能用、周边残缺、带安全隐患"——距离用户要的成品还差一个完整版本的工作量。**

本次审校**推翻了 v1.4.0 发布时"无 P0"的结论**。原因不是发布时审校造假，而是当时两轮 QA 的审查范围聚焦于"v1.4 改了什么"，没有拿全量验收标准回头核对历史遗留项。本轮补上了这个盲区。

## 二、P0 缺口（阻断"成品"定性，必须优先处理）

### P0-1｜Electron 33 已停止支持，且凭据加密用的是即将被移除的 API

- **现象**：`package.json` 锁定 Electron 33；`src/main/store/crypto.ts:7-21` 使用同步 `safeStorage.encryptString()` / `decryptString()` / `isEncryptionAvailable()` 加解密所有账号密码。
- **官方核实**（非推测，2026-11-22 查证）：
  - Electron 官方发布计划表：Electron 33 稳定版 2024-10-14，**2025-04-28 停止支持**；当前受支持版本为 43/44/45（46 即将稳定）。本项目落后约 19 个月。
  - Electron 官方 safeStorage 文档与 45.0 发布说明：**同步 API 已弃用，将在 Electron 46 移除**，替代为 `isAsyncEncryptionAvailable()` / `encryptStringAsync()` / `decryptStringAsync()`（异步非阻塞、支持密钥轮换），且明确"同步 API 加密的数据可由 `decryptStringAsync()` 解密"——即**迁移路径存在且向后兼容**。
- **影响**：用户明确要求"保证安全性"。运行在一个不再接收安全补丁的 Chromium/Node 上，且凭据保护依赖一个会被删除的 API，这是**随时间自动恶化**的安全债，不是风格问题。
- **建议**：升级到受支持版本（建议 45，避开 46 的破坏性变更窗口），同步迁移到异步 safeStorage API，用官方支持的兼容路径读取旧密文；补迁移回归测试（旧密文可读、新密文可解、密钥轮换 `shouldReEncrypt`）。

### P0-2｜会话生命周期整段缺失（REQ-010 零实现）

- **现象**：
  - 全项目**无 Electron `Tray` 实现**（全局搜索 `new Tray`/托盘菜单无结果）。
  - 全项目**无 disconnect / 结束会话入口**（IPC 通道只有 `SESSION_CONNECT`/`PRECHECK`/`LIST`，无断开通道）。
  - `src/main/session/manager.ts:48,79,152-156`：`state` 初始 `idle` → `connecting` → `connected`，**无任何路径回落 `idle`**；调起外部客户端瞬间即写 `endedAt = now()` 并标记完成，**从不跟踪外部进程退出**，也没有 in-flight 去重（重复点击可并发拉起多个客户端）。
- **影响**：验收标准 REQ-010 承诺的"托盘驻留 → 唤回主控 → 按需断开 → 回收"整段不存在；直接连带 REQ-009 的"会话时长"恒为 ≈0，历史记录里的时长字段是假数据。
- **补充证据**：`src/main/protocols/rdp.ts:137-160` 把含 DPAPI blob 的 `.rdp` 写入 `%TEMP%`，仅靠固定 8 秒 `setTimeout` 清理且失败静默忽略——mstsc 启动慢于 8 秒可能被删导致连接失败，启动快则密文残片留存。
- **建议**：实现托盘与会话回收闭环（详见设计方案 v1.5）；会话时长改为"外部进程存活时长"近似或明确标注"不可测量"，不再写假数据；`.rdp` 改为监听子进程退出后再清理 + 退出码兜底。

### P0-3｜REQ-009 一键重连 / 清空 / 设备筛选零实现

- **现象**：`src/renderer/src/components/History.vue` 只有一个只读 `el-table`（:52-77），**无重连按钮、无清空入口、无按设备筛选**。验收标准 REQ-009 明确要求这三项且"一键重连成功率 ≥95%"。
- **影响**：用户每次重连都要走完整的"选设备 → 选协议 → 输账密"流程，"下次直接进桌面"的体验承诺只兑现了一半（免密兑现了，重连入口没有）。
- **建议**：历史行加"一键重连"按钮（复用保存凭据直接 `session:connect`）、清空历史（带确认）、设备名/协议筛选。

### P0-4｜REQ-011 连通性自检的三类结论零实现

- **现象**：验收标准 REQ-011 要求"ping + 端口探测 → 分类结论（离线 / 端口未开 / 防火墙拦截）准确率 ≥90%"。实际 `PrecheckResult`（`src/shared/types.ts:217-224`）只有 `reachable: boolean` + `latencyMs`，`src/main/ipc/index.ts:57,60` 仅按端口给一句静态文案，**没有 ping、没有三类判定逻辑**。
- **影响**：用户拿到的是"通/不通"二元结果，而不是"为什么不通、去被控端做什么"的诊断结论——这正是用户反复抱怨的"不知道怎么用"的根源之一。
- **建议**：补 ICMP/ARP 存活探测 + 端口探测组合，输出三类枚举结论与对应行动指引，纳入诊断日志。

### P0-5｜空设备列表"重新加载"按钮断链（白板观感直接来源）

- **现象**：`src/renderer/src/components/DeviceList.vue:129-131` 空态按钮 `@click="emit('refresh')"`；`src/renderer/src/App.vue:200` 把 `refresh` 绑定到 `refreshDevices()`——**只重读列表，不触发扫描**。用户首次启动扫不到设备时点"重新加载"，界面原地打转。
- **影响**：与用户原话"给我一个完全无法使用的白板"直接对应。这是最低成本、最高感知价值的修复。
- **建议**：空态按钮改为触发扫描（emit `start`），并补"3 步排查清单"（同网段？被控端已开远控？防火墙放行？）+ 手动添加 IP 入口。

> 另注：`docs/02c` 的 REQ-001 也明确要求"扫描 0 台 → 3 步排查清单"，当前 `ScanPanel.vue` 无此内容，与 P0-5 合并修复。

## 四、P2 汇总（不阻断，纳入迭代池）

- 共享：xrdp 的 `native` 能力标注偏乐观；`README:151` 与代码口径不一；无效参数透传；RDP `domain` 参数实用性低。
- UX：视觉术语混用、空态文案专业味重、扫描耗时无预期提示。
- 工程：IPC 上帝文件（`ipc/index.ts` 持续膨胀）；无统一错误类型；日志轮转竞态；依赖未锁定 minor；无崩溃兜底 UI；无异常自动恢复。
- 测试：E2E 连接链路空白；外部客户端调起命令无断言；并发/失败路径覆盖不足；UI 交互零测试。
- 文档：多处 v1.3 历史版本号与新特性混排；能力矩阵表与代码常量存在细微分歧。

## 五、正面回答："这是半成品吗？"

分三层看，避免情绪化定性：

**1. 产品边界内——核心是真实的。** 按 `docs/02c` 的裁决，本产品定位是"发现 + 编排 + 配置 + 凭据 + 诊断"的外部调起器，画面渲染/键鼠/剪贴板同步明确不归本产品验收。在这个边界内，设备发现、协议推荐、RDP 免密、VNC/RustDesk 调起、SMB 打开、日志诊断——都是**真实跑通的代码**，不是空壳。**这一点上它不是半成品。**

**2. 但按自己的验收标准——有实质性违约。** 项目自己冻结了 02c 作为"唯一权威口径、P0 全部通过才放行"，而 REQ-009/010/011 三项 P0 处于零实现或失真状态，REQ-001 的 0 台排查清单也缺失。**按自己定的规则，v1.4.0 本不该被判定为"无 P0、可以发布"。**

**3. 按用户的体验预期——差距明显。** 用户要的是"完整可用且好用"。当前：空列表按钮原地打转、连上后无法真正"断开"、重连要重走全流程、连不上只告诉"不通"不告诉"为什么"、剪贴板/传文件的价值全靠外部客户端——这些叠加起来，正是"半成品感"的来源。

> **综合结论**：这是一个**骨架完整、核心可用、但功能闭环和体验细节没做完**的产品。它不是从零开始的半成品，而是一个"差最后一公里"的产品——问题集中在**会话生命周期、重连闭环、诊断闭环、安全底座**这四块，而非核心连接能力。

## 六、根因分析（为什么会这样）

1. **验收标准与实际实现脱节**：02c 定稿后，开发以"每个版本改了什么"为驱动，没有建立"每版回头全量核对验收标准"的机制，导致历史 P0 项长期悬空而无人察觉。
2. **"外部调起"边界被过度使用**：把不做什么（画面/键鼠）正确地排除了，却连带把"会话回收、重连、诊断结论"这些**本产品职责内**的事也一并忽略了。
3. **审校范围窄化**：v1.3/v1.4 的 QA 都聚焦"本次 diff"，缺少 fresh-eyes 的全量对照审校——本轮补上后立刻发现 5 个 P0。
4. **"测试全绿"造成虚假安全感**：218 个测试主要覆盖纯函数，核心链路（DPAPI、调起命令、失败分类、老库迁移）反而零覆盖。

## 七、审校方法与证据可信度

- **五维度独立审校**：产品完整性、共享能力、用户体验、工程健康度、测试有效性，各自只读审校、互不参照，最后交叉验证。
- **team-lead 独立核实**：对本报告所有 P0 逐条读码复核；Electron EOL 与 safeStorage 弃用两条**查证官方发布计划表与 API 文档**（2026-11-22），非二手推测。
- **不 rubber-stamp**：明确推翻发布时的"无 P0"结论；对 worker 报告中一条不准确的举例（`clipboard:i:1`）已纠正为实现真实的 `redirectclipboard:i:1`。
- **证据形式**：每条缺口标注文件:行号；涉及外部事实的标注官方来源。

> 升级完善设计、分版路线图与迭代滚动优化机制见 `docs/15-v1.5升级完善设计与迭代滚动优化.md`。

## 八、v1.5 发布前复核补充（2026-11-22，本报告最后更新）

> 背景：5 项 P0 实施完成后，在发布前做最后一轮独立复核。本轮不复用前面的审校结论，逐条读码核对"承诺 vs 实现"，又发现 3 处缺陷——其中 1 处是会影响用户判断的 P0。全部在本轮修复并补回归测试后才放行。

### 新增缺陷与处置

| 编号 | 级别 | 缺陷 | 证据 | 处置 |
|---|---|---|---|---|
| 补-1 | **P0** | `icmpProbe()` 仅凭 `execFile` 的 error 判"无法判断"。ping 离线主机时进程本就以非零码退出，于是 `icmpReachable` 恒为 null，REQ-011 的"设备离线"结论**永远无法出现**，用户连不上时拿不到最关键的一条指引 | `src/main/discovery/precheck.ts:197`（修复前） | 新增 `parsePingOutput()` 解析输出文本（先判失败信号再判回包，覆盖中英文文案与"目标主机无法访问"这类带 `Reply from` 的陷阱），`icmpProbe()` 合并 stdout/stderr 交给它 |
| 补-2 | P1 | R2-5 承诺 `.rdp` "进程退出后清理 + 30 秒兜底 + 失败记 WARN（哈希脱敏）"，实现仍是固定 8 秒静默清理 | `src/main/protocols/rdp.ts:150-159`（修复前）；`docs/15` 第 51 行 | 新增 `src/main/protocols/tempfile.ts`：`scheduleTempFileCleanup()`（宽限期 + 连续 2 次确认 + 30 秒兜底）、`removeTempFile()`（ENOENT 幂等、失败记 WARN）、`tempFileHash()`（sha256 前 12 位，不写路径）；rdp.ts 改用它 |
| 补-3 | P1 | `endSession()` 不检查当前状态：连接失败后 `state='failed'`，此时点"结束会话"会把已落库的 `failed` 记录改写为 `ended`，污染历史与诊断 | `src/main/session/manager.ts:213`（修复前） | `endSession()` 对 `failed` 终态短路返回 false，保留失败记录 |

**附带的结构调整**：进程存活检测 `isPidAlive()` / `taskListCsvShowsPid()` 从 `session/manager.ts` 抽到 `session/process-liveness.ts`，供 rdp 清理复用并避免 `protocols/rdp.ts → session/manager.ts → protocols/registry.ts → rdp.ts` 循环依赖；manager.ts 保留 re-export，既有导入路径不破坏。

### 复核后状态

- 三处缺陷全部修复，新增 **20 个回归用例**（`tests/v15-fixes.test.ts`、`tests/v15-failed-session.test.ts`），全量 **321/321（23 文件）** 通过。
- 修复过程中测试捕获到一个真实边界：Windows "目标主机无法访问"回复同样含 `Reply from`，若先判回包特征会误判在线——已通过"失败信号优先"顺序修正并固化为用例。
- 结论：5 项原始 P0 + 3 处发布前复核缺陷**全部清零**，v1.5.0 具备发布条件。

> 说明：本轮复核由 team-lead 独立完成（fresh-eyes 独立审校 agent 的通信通道在会话上下文压缩后失效），上述结论均基于实际代码与可复现测试，不依赖无法召回的 agent 报告。
