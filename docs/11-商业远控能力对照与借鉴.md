# 11｜商业远控能力对照与借鉴

> 版本：v1.3.0｜日期：2026-11-18｜状态：随 v1.3.0 交付
> 定位：逐项对照 RustDesk / 网易UU远程 / ToDesk / 玉兔远程控制 的能力形态，判断「哪些能借、哪些借不来」，作为 v1.3 取舍的事实依据。
> 阅读顺序：`10-v1.3底层架构与能力缺口梳理.md`（架构与边界）→ 本文（对照与借鉴）→ `12-v1.3可观测性与诊断方案.md`（可观测性落地）。

## 0. 结论先行（必须诚实的判断）

商业远控那些让人觉得「好用」的体验，几乎都建立在**三件套**之上：

1. **被控端常驻 Agent**：开机自启、常驻后台、无人值守、反向连服务端；
2. **云端信令 / 中继**：NAT 打洞协商、会话码路由、打洞失败时 relay 兜底；
3. **账号体系**：登录、设备列表云同步、权限、二次验证。

LanDesk 把这三件套**全部拿掉**了 —— 纯局域网、无服务端、不自研协议栈、不捆绑 AGPL/GPL、零遥测，这是产品根基而不是暂时缺功能。由此得出两条硬结论：

- **能借的是「产品形态与工程规范」**：设备发现、远程唤醒、收藏/别名/最近连接、审计、日志诊断 —— 这些是主控端本地功能，不依赖服务端与被控端 Agent，可以在本地重新实现。
- **借不来的是「协议能力」**：会话码、P2P 打洞、中继、2FA、端到端加密、自有文件传输通道 —— 这些要么需要服务端/常驻 Agent/账号体系，要么属于被调起通道自身的协议栈，LanDesk 既没有也不接触。

**严禁把「借不来」的协议能力写成「借鉴后已实现」或「本轮落地」。** 本文所有【本轮借鉴落地】仅指 `RELEASE_NOTES.md` v1.3.0 段明确列出的本地能力；协议能力一律归入【明确不做】或【后续演进】。商业产品的优秀不等于本项目要复刻，取舍理由见 §2、§4。

## 2. 能力维度逐项对照矩阵

标注含义：**【已具备】** 早已落地；**【本轮借鉴落地】** v1.3 以纯本地方式实现的产品形态；**【明确不做】** 与根基冲突，不列入待办；**【后续演进】** 候选方向，本轮不做（理由见 §6）。

| 能力维度 | 商业远控普遍做法 | LanDesk 现状 | 标注 | 取办理由 |
|---|---|---|---|---|
| 设备发现 | 账号下设备列表由云端同步（被控端 Agent 注册上线） | L1/L2/L3 分层扫描 + 只读服务指纹 + mDNS/ARP 辅助，本地按 IP 聚合 | 【已具备】+【本轮借鉴落地】 | 借鉴「自动标识设备、少手填」的产品形态，但用本地扫描实现，不引入账号/云端；本轮再扩展 mDNS 服务类型（见 §3） |
| 远程唤醒 | 云端下发唤醒指令 / 被控端 Agent 保活 + WoL | 本轮新增 UDP Magic Packet 本机广播唤醒（best-effort、无回执） | 【本轮借鉴落地】 | 借鉴「一键唤醒」形态，用标准 WoL 魔术包本地实现；不依赖云端、不装常驻 Agent。限制见 §3 |
| 在线状态 | 被控端 Agent 心跳 → 实时在线/离线 | 扫描时刻的存活快照（非实时） | 【后续演进】 | 轻量在线心跳需解决 sql.js 每次 upsert 全量 persist 的写放大问题（「状态翻转才落库」+ 窗口失焦降频），属独立工程项，本轮不做（§6） |
| 收藏 / 别名 / 最近连接 | 账号云端保存，一键重连 | 连接历史本地留存 + 手动添加 IP | 【后续演进】 | 需 `ALTER TABLE` 加列；本轮聚焦连接可用性与可观测性，避免范围膨胀导致验证不充分（§6） |
| 文件传输与剪贴板 | 自有传输通道、可断点续传、账号/云端中转、会话内剪贴板 | 全量复用 RDP 磁盘重定向 / SMB（资源管理器）/ RustDesk 客户端 / VNC Viewer 原生能力 | 【已具备】（复用） | 不自研传输协议、不经手内容；**Explorer 的 SMB 复制不支持可靠断点续传，现有「传文件」通道不承诺断点续传** |
| 安全机制 | 2FA、防暴力破解、账号权限、自有 E2EE | 依赖被调起通道：RDP TLS+CredSSP/NLA（不降级）、RustDesk 客户端自带 E2EE、VNC 明文警示 + 引导改道 | 【已具备】（边界披露） | LanDesk 不接管认证、不接触媒体流，**不提供也不宣称提供端到端加密**；2FA / 防暴力破解 / 自研 E2EE 属【明确不做】 |
| 会话码 / 打洞 / 中继 | 核心能力：会话码 + P2P 打洞 + relay 兜底 | RDP/VNC/SMB 本就是 `IP:端口` 端到端直连，无中转 | 【明确不做】 | 需信令服务 + 中继 + 常驻 Agent + 账号体系，与「无服务端、零遥测、不捆绑」根基冲突；局域网内直连已是最低延迟路径（详见 `docs/10` §2） |
| 日志诊断 | 云端日志 / 审计 / 会话统计（时长、码率、帧率） | 本轮结构化 JSONL 本地日志 + 运行状态快照 + 一键导出诊断包，纯本地、零遥测 | 【本轮借鉴落地】 | 借鉴「可查询、可导出、可审计」的工程规范，落地为本地结构化产出 + 用户主动导出（见 `docs/12`）；会话级媒体统计【明确不做】 |

**一句话读表**：能借的（发现、唤醒、审计、日志）都已经或正在以「纯本地形态」落地；借不来的（会话码、打洞、中继、2FA、E2EE、自有传输通道）一律不写进能力清单，也不伪装成「借鉴后已实现」。

## 3. 事实校准：mDNS 与协议识别（避免误写）

对照商业远控「设备自动出现在列表里」的体验时，容易误以为 mDNS 能覆盖所有系统。真实情况必须写清，避免文档夸大：

- **Windows 原生远程桌面默认不通过 mDNS 广播 RDP**：`_rdp._tcp` 在真实环境基本收不到。RDP 识别主力是 **3389 端口 + X.224 Connection Confirm 握手层指纹**（`docs/09` L3），不是 mDNS。
- **本轮 mDNS 服务类型扩展**（本地解析，不依赖云端，含 UDP 类型记录与 TXT 解析）：

| 服务类型 | 端口 | 说明 |
|---|---|---|
| `_rfb` | 5900 | macOS 屏幕共享 |
| `_net-assistant` | 3283 | **UDP 类型**服务记录 |
| `_smb` | 445 | 文件共享 |
| `_ssh` / `_sftp-ssh` | 22 | Linux / NAS |
| `_afpovertcp` | 548 | AFP |
| `_device-info._tcp` | — | TXT 记录 `model` / `osxvers`，用于细化设备型号与系统版本 |

- **飞牛OS（fnOS）没有稳定公开的专属 mDNS 类型**，不要编造；现靠 **HTTP `Server` 头 + 5666 端口**识别。
- 这些都是「本地服务类型发现」，与商业远控「账号下设备列表云同步」不是一回事；扫描仍只到握手识别层，不进鉴权 / TLS / NLA、不采集证书、无口令或破解逻辑。
- **WoL 的准确边界**：UDP Magic Packet 为 **best-effort、无回执**，需被控端 BIOS/网卡预先开启 WoL 且处于可唤醒供电状态，**跨网段通常无效**；LanDesk 只发本机魔术包，不保证唤醒成功、不引入被控端常驻 Agent。

## 4. 明确不做清单（完整，避免被当成遗漏）

| 排除项 | 为什么不做 |
|---|---|
| 会话码 / 设备 ID 注册 | 本质是向服务端登记设备，需账号体系与信令；与「不采集、不上传设备信息」冲突 |
| P2P 打洞 / NAT 穿透 | 需公网 rendezvous/信令服务器；局域网内本就是 `IP:端口` 直连，无收益 |
| 中继服务器 / relay 转发 | 引入中转即破坏「端到端直连、无中转」定位，并产生服务端运维与隐私责任 |
| 信令服务 / rendezvous | 同上，且要求被控端与服务端保活注册 |
| 无人值守 / 被控端常驻自启 Agent | 要求被控机新装常驻程序，超出「被控端用现成服务、不新装程序」边界 |
| 账号体系 / 登录 / 设备云同步 | 需中心服务与用户数据托管，与「无账号、无服务端」冲突 |
| 2FA / 二次验证 | 依赖账号体系与服务端校验，本地单体无从承载 |
| 防暴力破解（服务端限流 / 封禁） | 属服务端或被控端策略；LanDesk 不接管认证，不宣称提供 |
| 端到端加密（自研 / 宣称） | **由被调起的通道提供**（RDP TLS、RustDesk 客户端 E2EE）；LanDesk 不提供、不控制协商，也**不宣称提供**（详见 §5） |
| 自研文件传输协议 | 全量复用 RDP 重定向 / SMB / 客户端原生能力，不自研、不经手内容 |
| 常驻剪贴板同步（断开会话后仍同步） | 需中心服务，与「无服务端」定位冲突 |
| 会话时长 / 码率 / 帧率统计 | 画面与媒体流由外部客户端承载，LanDesk 不接触，无从采集也不采集 |
| 内建 SSH / VeNCrypt 隧道 | 属 Viewer 与服务端协商的协议栈能力，LanDesk 只 `spawn` 调起、不控制协商；不内嵌 GPL/AGPL 栈 |
| 内嵌 AGPL/GPL 协议栈、VNC 画面自研渲染 | 许可传染 + 超出「外部调起」模型，属重新立项范畴 |
| 云端遥测与诊断上报 / 崩溃自动上报 / 任何遥测外发 | 零遥测承诺；诊断数据仅本地产出，是否分享由用户主动决定；设置中默认关闭的预留开关（`telemetryConsent`）当前不产生任何采集或上报行为 |

## 5. 安全事实（协议层，绝不夸大）

对照商业远控「端到端加密」宣传时，必须把各通道的真实归属写清，避免把通道能力算到 LanDesk 头上：

- **RDP**：保持 **TLS + CredSSP/NLA 默认不降级**；不为免密关闭安全协商，Credential Guard / 空密码账户自动回退手输，不绕过系统策略。
- **RustDesk**：官方客户端**自带 E2EE** —— 这是被调起的独立客户端提供的能力，LanDesk 不提供也不宣称提供。
- **VNC / RFB（重点）**：基础 RFB 只有 **None / VncAuth** 两种安全类型；**VncAuth 仅保护最多 8 字符密码**，而**帧缓冲、键鼠、剪贴板全部明文传输**。要做到加密需 **VeNCrypt / SSH 隧道**，且**取决于 Viewer 与服务端协商结果**；LanDesk 只 `spawn` 调起 Viewer，**不控制、不参与、也无法保证该协商**。
- 因此 **绝不宣称「VNC 已加密」**。LanDesk 只做两件事：使用前警示（**仅限可信局域网**）+ 引导改道到更安全的通道（**RDP / RustDesk / SMB**）。标准 VNC 不含文件传输。

> 与 `README.md` 第八节、`docs/10` §6 口径一致：LanDesk 自研的是发现/编排/凭据/诊断，不是远程桌面协议，更不是加密协议。

## 6. 后续演进（本轮不做，逐项写明理由，避免被当成遗漏）

| 演进项 | 本轮不做的原因 |
|---|---|
| 轻量在线心跳 | sql.js 每次 upsert 会全量 persist，频繁写造成写放大；需「状态翻转才落库」+ 窗口失焦降频，属独立工程项 |
| 收藏 / 置顶 / 别名 / 最近连接一键重连 | 需 `ALTER TABLE` 加列；本轮聚焦连接可用性与可观测性，避免范围膨胀导致验证不充分 |
| SMB `robocopy /Z` 断点续传 | 会外扩「只调起、不经手内容」的边界；且现有 Explorer 通道本就不承诺断点续传 |
| SSH 终端入口 | 属新的连接协议通道，需 SSH 客户端依赖与独立鉴权模型，超出「只调起既有远桌面」范围，独立评估 |
| WS-Discovery / NetBIOS 补 Windows 主机名 | 新增发现手段与依赖，需独立评估，不属于本轮 mDNS 扩展范围 |
| 诊断包另存为（`dialog.showSaveDialog` 用户自选路径）与导出前勾选包含项 | 属诊断侧交互演进，理由见 `docs/12` §10 |
| 状态快照补 `capabilityMatrix` 静态能力矩阵副本 | 属快照字段演进，理由见 `docs/12` §10 |
