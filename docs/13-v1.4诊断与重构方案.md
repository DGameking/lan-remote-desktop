# LanDesk v1.4 诊断与重构方案（通盘考虑稿）

> 起因：2026-11-22 用户实测反馈三点——① 扫描选错网段（显示 172.27.112.0/24，路由器实际是 192.168.10.0/24）；② 系统类型识别几乎全为「未知系统」；③ 协议口径含糊（VNC/RFB 未讲清、功能分级与 UI 是否需要升级）。
> 本文先以官方/权威资料校准事实，再逐项给出根因与重构方案，最后给出分期开发清单。
> **实施状态：A/B/C/D/E 均已落地并通过验证，详见文末「六、实施记录」（v1.4.0）。**

## 一、官方资料校准（先统一事实，不凭记忆）

### 1. RFB 与 VNC 的关系
- **RFB（Remote Framebuffer）是协议，VNC 是使用该协议的远控技术**。RFC 6143（2011，IETF）是 RFB 的权威规范。
- RFC 6143 §7.1.1 明确：官方版本号只有 `003.003`、`003.007`、`003.008`，横幅格式为 `RFB xxx.yyy\n`。
- RFC 6143 §6 原文：*"Under no circumstances should an implementation use a protocol version number other than one defined in this document"*，且 *"any unknown 3.x version must be treated as 3.3"*。
- 结论：**`003.889` 不是官方 RFB 版本**，它是 Apple 的私有版本号。

### 2. macOS 屏幕共享的真实协议
- Apple 官方（support.apple.com/103229）：`5900 TCP` 服务名 `rfb`，用于 **Apple Remote Desktop / 屏幕共享**；另有 `3283 TCP/UDP`（`net-assistant`，ARD 报告与附加数据）；`5900 UDP` 传屏幕（RTP/RTCP）；SSH（22）可做加密文件传输与隧道。
- Apple 官方（Remote Desktop 端口参考）：5900 TCP 控制观察、5900 UDP 发送屏幕、3283 报告、22 加密文件传输。
- Apple 屏幕共享 = **标准 RFB/VNC + Apple 私有扩展**：ARD 认证（Mac 用户名密码，非简单 VNC 密码）、文件传输、剪贴板同步、拖拽、手势编码；`003.889` 是被广泛观测到的 ARD 版本横幅（社区与第三方客户端实现一致确认，如 noVNC issue #58、gtk-vnc），`003.889` 应按兼容规则视作 3.3 握手。
- 结论：**「macOS 屏共享 = VNC」技术上成立，但它是增强版 VNC**。LanDesk 只调起第三方 Viewer，能连画面和键鼠，**拿不到 Apple 私有扩展（ARD 认证/文件传输/剪贴板同步）**。

### 3. Windows RDP
- 微软官方（MS-RDPBCGR）：RDP 基于 ITU T.120 扩展，多通道（最多 64000 通道）；**默认服务端口 3389 TCP+UDP，可改**。
- 微软官方（RDP 特性）：支持剪贴板映射、驱动器/打印机/端口重定向、声音重定向——印证 v1.1 共享能力走 RDP 原生通道的设计正确。
- 结论：**RDP 与 VNC/RFB 是完全不同的两套协议栈**，不可混为一谈。

### 4. Linux 与飞牛OS
- 飞牛OS 官方：**基于 Debian 发行版深度开发的 Linux NAS 系统**，没有专属远程桌面协议。
- Linux 桌面：VNC（TigerVNC/x11vnc 等，5900）或 xrdp（RDP 服务端，3389），取决于装了什么。
- 飞牛官方 FN Connect 是公网 P2P 远程访问服务，**不属于局域网直连范畴**，本项目不接入。
- 结论：**Linux/飞牛没有"一种"远程桌面协议**，必须按实际开放的服务判定。

## 二、根因诊断（对应用户三点反馈）

### 问题 1：网段选错（核心 bug）
现象：路由器后台显示所有终端在 `192.168.10.0/24`，LanDesk 显示 `172.27.112.0/24`，且扫出 `172.18.0.1`。

根因链：
1. `detectSubnets()`（`src/main/discovery/subnet.ts`）从 `os.networkInterfaces()` 枚举所有非 internal 的 IPv4，按 `isPrivateIp` 排序（私有优先）。
2. `172.27.112.x`（虚拟网卡，疑似 VPN/Hyper-V/VMware 之类）和 `192.168.10.x`（真实路由器网段）**都满足 isPrivateIp**，排序权重相同，稳定排序后取了第一个网卡 → 选中虚拟网卡。
3. `manager.ts:start()` 只扫描 `this.subnets[0]`，全部资源投入错误网段。
4. mDNS 汇总（manager.ts:168-188）**未按目标网段过滤**，把 `172.18.0.1`（WSL2/Docker 网关段）当作候选设备混入。

结论：**这不是"用户网络特殊"，是本项目的确定性缺陷**，必须修。

### 问题 2：系统识别几乎失效
现状（`src/main/discovery/aggregator.ts:inferOsHint`）：
- 只用 4 条规则：RFB `003.889`→macOS、SSH linux banner→Linux、HTTP fnOS→飞牛、3389→Windows，加名称关键字兜底。
- 缺：MAC OUI 厂商前缀、TTL 推断、mDNS TXT（`model`/`osxvers`/`Mac`）到 osHint 的映射、标准 RFB `003.008` 无法确定系统。
- 截图里两台设备 5900 开放但报的是标准版本（非 003.889），全部落到 `unknown`。

结论：**识别信号层级太薄，且没有置信度概念**——不确定时硬显示"未知系统"，用户无法判断可信度。

### 问题 3：协议口径 / 功能分级 / UI
- 代码层：`CAPABILITY_MATRIX` 有初步分级，但 UI 只显示"可用协议"徽章，未说明**每个协议能做什么、不能做什么**（如 VNC 无文件传输、Apple 私有扩展拿不到）。
- 用户看到两台"未知系统 + VNC"，无法判断该用什么协议、连上后有什么能力。

## 三、重构方案（v1.4）

### 模块 A：网段选择重构（P0）
1. **识别主网卡**：读系统默认路由（`route` 命令 / `os.networkInterfaces` + 网关探测），把有默认网关的物理网卡作为主网段。
2. **排除虚拟网卡**：按网卡名关键词（vEthernet、WSL、Docker、VMware、VirtualBox、TAP、TUN、Hyper-V、VPN、Lo）、以及 `172.17-31.x` 常见的容器/虚拟段特征降权。
3. **多网段可见 + 可切换**：UI 顶部显示识别到的所有网段，标记"主网段/虚拟网卡"，默认选主网段，允许手动切换。
4. **mDNS/ARP 过滤到目标网段**：跨网段的 mDNS 记录不再混入候选列表（彻底消除 `172.18.0.1` 误报）。
5. **手动网段输入**：允许用户输入 `192.168.10.0/24` 强制扫描。

### 模块 B：系统识别重构（P0）
建立**分层置信度**识别（强→弱），输出 `osHint + confidence + evidence`：
- **L1 强信号**：RFB 3.889→macOS（高置信）、RDP X.224→Windows、SSH banner 发行版→Linux、HTTP Server fnOS→飞牛。
- **L2 中信号**：mDNS TXT（model/osxvers/Mac→macOS，manufacturer/server→厂商）、MAC OUI 前 3 字节→厂商→系统族（Apple→macOS、Huawei/Xiaomi→多为手机/平板，标注"移动设备"而非硬判系统）。
- **L3 弱信号**：TTL（64→Linux/macOS，128→Windows，仅参考）、端口组合、设备名关键字。
- **UI 呈现**：设备行显示系统图标 + 置信度（如"macOS · 高"），不确定显示"未识别 · 请手动指定"，并提供手动选择系统的入口（人工确认优先于猜测）。

### 模块 C：协议能力分级（P1）
把 `CAPABILITY_MATRIX` 升级为「系统 × 协议 → 能力」矩阵，每项标明：
- 画面控制（基础）、剪贴板、文件传输、音频、免密、加密。
- 明确标注"由被调起客户端提供，LanDesk 不提供"的项。
- UI 在连接对话框展示该组合的能力清单与限制（如"macOS/VNC：可控制画面键鼠；剪贴板与文件传输取决于 Viewer 是否实现 Apple 扩展，本软件不保证"）。

### 模块 D：UI 规划与升级（P1）
1. 顶部网段选择器（主/虚拟/手动三段）。
2. 设备列表：系统图标 + 置信度徽章 + 协议能力标签 + 识别依据（可展开）。
3. 设备详情侧栏：开放端口、指纹证据、识别依据、可用能力、已知限制。
4. 连接对话框：按系统×协议显示能力矩阵提示与连接前置条件（如 Windows 需专业版、macOS 需在共享里开屏幕共享）。
5. 无设备时的引导式排查（网段是否正确 → 对方是否开服务 → 防火墙）。

### 模块 E：自我迭代机制（P2）
1. 诊断包增加"识别证据"字段，便于把误判案例反馈给用户核对。
2. 用户提供真实局域网抓包/截图 → 校正识别规则（如某品牌 NAS 的 mDNS TXT 特征）。
3. 识别规则表外置为可更新数据（不硬编码），便于迭代不重新编译。

## 六、实施记录（v1.4.0）

用户裁决后一次性完成 A/B/C/D/E，实际落地如下：

### A 网段选择重构
- `subnet.ts`：`classifyInterface()` 按网卡名 + 172.17~31 段识别虚拟网卡；`detectPrimaryInterfaceIp()` 用系统默认路由定位真正上网网卡（Windows `route print`，PATH 无 route.exe 时用 SystemRoot 绝对路径兜底；非 Windows 用 `ip route`/`route -n get`）；`sortSubnets()` 排序权重修正为「主网卡 > 物理 > 私有 > 虚拟垫底」——主网卡优先级高于虚拟惩罚，避免真实 172.x 主网段被误降权（QA P1-1）。
- `subnetContainsIp()` 用 CIDR 归属判断（含 prefix 合法性校验）；`parseManualSubnet()` 支持 CIDR 与单 IP 两种写法，/8~/23 宽网段收敛到 /24 避免误导。
- `manager.ts`：`start(targetCidr?)` 支持指定网段；mDNS 汇总按目标网段过滤，彻底阻断 `172.18.0.1` 等跨网段记录混入。
- 全链路：IPC `discovery:subnets` 下发网段列表、`discovery:start` 接收目标 CIDR；UI 顶部网段选择器（主网段/虚拟网卡标记 + 手动输入）。

### B 系统识别分层置信度
- 新建 `os-detect.ts`（纯函数）：`detectOs()` 输出 `osHint + confidence(high/medium/low/none) + evidence[]`。
  - L1 强信号：RFB 003.889→macOS、RDP X.224→Windows、SSH 发行版 banner→Linux、fnOS Server 头→飞牛OS。
  - L2 中信号：Apple MAC OUI（前 3 字节）、mDNS TXT 机型字段、AFP 服务。非 Apple OUI 不硬判系统，避免手机/路由器误报。
  - L3 弱信号：默认端口、TTL、设备名关键字；标准 RFB 003.008 不臆测系统。
- `aggregator.ts` 接入分层识别；用户手动指定的系统写入 `osManual` 锁，后续扫描不再覆盖。
- 设备行显示系统图标 + 置信度徽章（高/中/低/未识别），可展开查看识别依据、手动指定系统。
- 存储层兼容升级：SQLite 老库 ALTER 补列、JSON 库补默认值，历史设备零丢失。

### C 协议能力分级矩阵
- `SYSTEM_PROTOCOL_MATRIX`：系统 × 协议 → 能力分级（native/client/limited/none），覆盖 Windows/macOS/Linux/飞牛 × RDP/VNC/RustDesk，标明剪贴板、文件传输、画面控制与连接前置条件。
- 连接对话框按「系统 × 协议」展示能力说明与前置条件（如 macOS VNC 剪贴板为 limited、取决于 Viewer 是否实现 Apple 私有扩展）。

### D UI 规划升级
- 网段选择器、置信度徽章、识别依据展开、手动指定系统、连接前协议能力提示、引导式排查（沿用并强化）。

### E 自我迭代机制
- 识别证据以 `os.detected` 结构化事件回流到本地诊断日志（IP 保留、MAC 不写），用户导出诊断包即可反馈误判案例，据此校正 `os-detect.ts` 中的规则表（规则集中在纯函数文件，迭代无需改动扫描/存储链路）。

### 验证结果
- typecheck ✓ / typecheck:vue ✓ / test:unit 218/218（v1.3 基线 169 + v1.4 新增 49）/ build 三进程 ✓ / dist ✓。
- QA 独立审查 A 模块发现的 P1-1（主网卡排序）、P2（route 路径、prefix 校验、宽网段收敛）已全部修复并补回归测试。
