# 15｜v1.5+ 升级完善设计与迭代滚动优化机制

> 日期：2026-11-22｜依据：`docs/14-v1.5全面审校报告.md` 的 5 项 P0 / 12 项 P1 / P2 池
> 目标（用户原话）：**"功能完整可用且好用的产品，而不是一个半成品"**；**"能不能进行自我迭代？"**
> 原则：守住既有根基（纯局域网 / 无服务端 / 无公网 / 无账号 / 零遥测 / 外部调起 / 不内嵌 GPL-AGPL），只补"产品边界内的功能闭环与体验短板"。**明确不做项不因本设计松动。**

## 一、设计总纲

### 1.1 补什么、不补什么

| 分类 | 本设计要补的 | 明确不碰的 |
|---|---|---|
| 安全底座 | Electron 升级 + 凭据加密 API 迁移 | 不打洞、不中继、不自研 E2EE、不引入遥测上报 |
| 功能闭环 | 会话生命周期、一键重连、连通性自检三类结论、0 台排查 | 不渲染远程画面、不自研协议栈、不做键鼠映射 |
| 体验 | 空态断链、认知图例、失败可执行指引、免密可见 | 不为了好看牺牲"无账号/纯本地"根基 |
| 迭代机制 | 诊断证据回流、版本列车、审校 SOP、质量门禁 | 不收集用户数据（反馈靠用户主动导出诊断包） |

### 1.2 三个版本的节奏

```
v1.5.0 稳定与安全版  ← 清 5 项 P0，把"能用"变成"敢长期用"
v1.6.0 好用与闭环版  ← 清 12 项 P1，把"能用"变成"好用"
v1.7.0+ 演进池       ← P2 + 用户反馈驱动的滚动迭代
```

每版独立走：设计锁定 → 实现 → 全量验证 → fresh-eyes 独立审校 → 发布。**任一版 P0 未清，不进下一版。**

## 二、v1.5.0 稳定与安全版（P0 清零）

### 2.1 范围与逐项实施清单

#### R1｜Electron 升级 + safeStorage 异步迁移（P0-1）

- **做什么**：Electron 33 → 45（受支持版本，避开 46 的同步 API 移除窗口）；`crypto.ts` 迁移到 `isAsyncEncryptionAvailable()` / `encryptStringAsync()` / `decryptStringAsync()`，全部改为 async 并向上冒泡到 IPC handler。
- **兼容**：官方明确"同步 API 加密的数据可由 `decryptStringAsync()` 解密"，因此**老用户已存凭据无需清除**；实现时先尝试异步解，失败再明确提示重新输入（不静默丢数据）。
- **改哪些文件**：`package.json`、`src/main/store/crypto.ts`、`src/main/store/index.ts`、所有调用 `encryptPassword`/`decryptPassword` 处（`session/manager.ts`、`ipc/index.ts`）、`tests/rdp-auth.test.ts`、`tests/settings.test.ts`。
- **验收**：① Node/Chromium 升级后 typecheck/typecheck:vue/test/build/dist 全绿；② 用旧版密文样本可解出正确明文（迁移回归）；③ 新密文可解；④ `npm audit` 无 high/critical；⑤ 打包后首次启动无 crash（人工冒烟）。
- **风险与对策**：大版本跳跃可能触发 Chromium/Node 行为变更 → 先在独立分支跑通全量验证再合并；保留 `GIT_SSL_NO_VERIFY` 的本地 push 规避方式。

#### R2｜会话生命周期闭环（P0-2）

- **做什么**：
  1. 引入 Electron `Tray`：调起外部客户端后主控最小化到托盘，托盘菜单提供"回到主控 / 结束会话 / 退出"。
  2. 外部进程退出检测：Windows 用 `tasklist`/WMI 按进程名 + 命令行特征 polling（间隔 3-5s），检测 mstsc/vncviewer/rustdesk 退出 → 二次确认窗口状态后回收（防单实例假退出，遵循 02c §5）。
  3. `SessionManager` 状态机补 `idle` 回落与 in-flight 去重（同一 device+protocol 正在 connecting 时拒绝重复调起）。
  4. 会话时长改为"外部进程存活时长"近似；无法测量时明确写 `durationUnavailable: true`，**不再写 `endedAt = startedAt` 的假数据**。
  5. `.rdp` 临时文件改为"检测到进程退出后清理 + 进程未找到时 30 秒兜底"，替代固定 8 秒；清理失败记 WARN 日志（含文件哈希不含路径）。
- **改哪些文件**：`src/main/index.ts`、`src/main/session/manager.ts`、`src/main/protocols/base.ts`、`rdp.ts`、`src/shared/types.ts`、`src/preload/index.ts`、`src/main/ipc/index.ts`、`History.vue`。
- **验收**：REQ-010 全流程可走通（调起 → 托盘 → 唤回 → 结束 → 记录）；重复点击不产生两个客户端；`.rdp` 在进程退出后 5s 内被清理；会话时长不再恒为 0。

#### R3｜一键重连 / 清空 / 筛选（P0-3）

- **做什么**：`History.vue` 每行加"一键重连"（用已存凭据直接 `session:connect`，跳过协议选择）；顶部加"清空历史"（确认框）与按设备/协议筛选；新增 IPC `SESSION_RECONNECT`（或复用 connect + `reconnectFrom` 字段）。
- **验收**：REQ-009 三项可用；一键重连成功率在本地测试中 100%（失败时回到凭据步骤并保留历史）。

#### R4｜连通性自检三类结论（P0-4）

- **做什么**：`SessionPrecheck` 返回 `conclusion: 'offline' | 'port_closed' | 'firewall_or_auth' | 'reachable'` + `actions: string[]`。实现：先 TCP 端口探测（`precheck.ts` 已有）→ 不通时对目标 IP 做 ICMP ping（Windows `ping -n 1 -w 1000`，无管理员权限）→ ping 通则判 `port_closed`/`firewall_or_auth`，ping 不通判 `offline`。UI 按结论展示可执行指引（被控端开服务 / 放行防火墙 / 确认同网段）。
- **验收**：模拟 4 类场景，分类结论与实际情况一致；结论进入诊断日志（仅 IP + 枚举结论，不含凭据）。

#### R5｜空列表断链 + 0 台排查清单（P0-5）

- **做什么**：`DeviceList.vue` 空态按钮从 `emit('refresh')` 改为 `emit('start-scan')`；`App.vue` 绑定 `startScan`；空态内嵌"3 步排查清单"（同网段？被控端已开远控？防火墙放行 3389/5900？）+ "手动添加设备"直达按钮（跳设置页并聚焦）；`ScanPanel.vue` 扫描 0 台时展示同样清单。
- **验收**：首次启动扫不到设备 → 点"重新扫描"真的扫描；排查清单 100% 可见；能一键到手动添加。

### 2.2 v1.5 交付物

- Release `v1.5.0` + 更新 README "已知限制"（会话生命周期不再写"不支持"）、RELEASE_NOTES、项目档案、docs/14 回填"P0 已清零"。

## 五、迭代滚动优化机制（回答"能不能自我迭代"）

> **先讲清边界**：LanDesk 无服务端、零遥测、无对外 API，**任何 AI / 云端都无法远程连进本软件实时读状态**。因此"自我迭代"不是软件自动联网上报、AI 自动改代码——那与根基冲突。可行且诚实的形态是：**本地结构化证据 + 用户主动转交 + 固定审校 SOP + 版本列车**。这套机制让每一次真实使用都能沉淀为下一次优化的证据。

### 5.1 证据回流闭环（核心）

```
用户使用 → 本机写结构化日志(jsonl) + 诊断包(traceId 串联)
        → 用户主动"复制诊断文本"或导出文件交给 AI
        → AI 按 SOP 审校 → 产出缺口清单(带行号证据)
        → 缺口进入 docs/14 的 P0/P1/P2 池
        → 版本列车规划 → 实现 → 验证 → 独立审校 → 发布
        → 新版本诊断字段更完善 → 下一轮证据更精准
```

关键设计：
- **诊断包要"自证充分"**：每个连接事件带 `traceId`，串起 预检结论 / 凭据决策 / 调起命令摘要（脱敏）/ 进程存活与回收 / 失败分类；只需用户复制一次文本就能定位。
- **识别规则集中可迭代**：`os-detect.ts` / `fingerprint.ts` / `subnet.ts` 的规则已是纯函数集中管理，误判案例可直接加规则 + 回归测试（v1.4 已建立此基础，本轮巩固）。
- **误判/失败有专属标记**：日志里 `os.detected` 置信度低、自检结论 `port_closed` 等，都可作为"证据密度不足"的信号，提示下一版补哪些字段。

### 5.2 用户反馈入口（不改"零遥测"）

- GitHub Issues 模板三类：① 连不上（附诊断文本）；② 识别错误（附诊断文本 + 正确系统）；③ 体验建议。
- README 明确"如何导出诊断文本"的三步操作（已有第十节，v1.5 强化为失败时自动提示）。
- **绝不**引入自动上报、崩溃回传、使用统计；用户不主动给，就没有任何数据离开本机。

### 5.3 版本列车（发布节奏）

- 每 2-4 周一列，或按 P0 清零触发（P0 优先，不等档期）。
- 每版固定五道门禁（见 5.4），**任一失败不发版**。
- 版本语义：`x.y.0` = 功能版（P0/P1 清零），`x.y.z` = 修复版（单个回归/bug）。

### 5.4 质量门禁（每版硬卡点，写入 CI）

| 门禁 | 内容 | 当前状态 |
|---|---|---|
| 类型 | `typecheck` + `typecheck:vue` | 已有 |
| 单测 | `test:unit` 全绿 + 核心路径覆盖不得为 0 | 已有（补覆盖率断言） |
| 构建 | `build` + `dist` 三进程产物完整 | 已有 |
| 验收对照 | **每版对照 `docs/02c` 全量核对 P0 项**，结果写入当版审校报告 | 本轮新增（这正是 v1.4 漏掉的） |
| 独立审校 | fresh-eyes 审校结论"可以发布"且无 P0 | 本轮固化 |

### 5.5 审校 SOP（可复用，防止再次漏项）

1. **五维度并行审校**：产品完整性（对照 02c 逐项）、共享能力、用户体验、工程健康度、测试有效性——各自只读、互不参照。
2. **team-lead 交叉核实**：每条 P0 亲自读码复核；涉及外部事实（如 Electron 支持状态）必须查官方来源。
3. **不 rubber-stamp**：明确允许推翻此前"无 P0"结论；纠正 worker 的不准确举例。
4. **缺口入池**：按 P0/P1/P2 写入 `docs/14`，每条带文件:行号与证据。
5. **版本映射**：缺口 → 版本（P0→v1.5，P1→v1.6，P2→演进池），逐版清零。

### 5.6 迭代的"记忆"——文档即状态

- `docs/00-项目档案.md`：每版交付记录（起因/改动/验证/发布状态）。
- `docs/14`：当前缺口池（活的清单，每版更新状态）。
- `docs/15`：本设计与版本路线图（滚动更新）。
- 工作日志 `.workbuddy/memory/YYYY-MM-DD.md`：每次实质性工作 append。
- 这样任何一次新会话，AI 读这几份文档即可接续，不依赖上下文记忆——**这就是本项目可跨会话"自我迭代"的实际载体**。

## 六、验收标准：什么样才算"完整可用且好用的成品"

全部满足才可对外宣称"成品"：
1. `docs/02c` 的 REQ-001~012 **逐项通过**，P0 缺陷 = 0（本轮已证明 v1.4 未达标）。
2. 新用户**不读 README** 也能在 5 分钟内连上第一台设备（空态有引导、失败有可执行结论）。
3. 会话有完整生命周期：调起 → 托盘 → 唤回 → 断开 → 记录（时长真实或明确标注不可测）。
4. 依赖在官方支持期内，凭据加密用官方推荐 API，迁移路径有回归测试。
5. 五个审校维度均无 P0，核心路径测试零盲区。
6. 用户可仅凭一份诊断文本让 AI 定位任意一次连接问题。

## 七、风险与取舍

- **Electron 大版本升级**是 v1.5 最大风险点：收益（安全）明确，但可能引入构建/行为回归。对策：独立分支先跑通全量验证，不滚动发布半成品。
- **外部进程退出检测**在 Windows 上无完美方案（mstsc 单实例复用会导致假退出），02c 已要求"二次确认"，本设计沿用，不承诺 100% 精确。
- **一键重连**必须尊重"改用户名但密码留空不回填旧密码"的安全策略（`credential-policy.ts`），不能为体验绕过。
- **不因"好用"牺牲根基**：所有体验改进都在本地完成，不引入账号、云同步、遥测上报。
