# 17｜C 类能力可行性评估（产品重新定义决策依据）

> 版本：v1.0｜日期：2026-11-22｜状态：供用户拍板的决策文档
> 触发：`docs/16` 把"一般远程桌面软件的功能我都需要"分层为 A/B/C 三类后，用户明确要求**重新评估 C 类，可能要做**。
> Objective：让用户据此拍板——**是否推翻现有定位、把 LanDesk 重做成全栈远控**。
> 口径：本文只做可行性与代价评估，**不修改任何冻结口径**。凡本文建议要做的事项，均须先走第七节的前置决策与文档修订，不得直接写进实现清单。
> 关联：`docs/02c`（冻结验收）、`docs/10`（架构与边界）、`docs/11`（商业对照与负向清单）、`docs/16`（A/B/C 分层）、`README.md`（产品定位与负向清单）。

## 〇、结论先行（TL;DR）

1. **C 类 9 项里，有 8 项不是"加功能"，而是"新建子系统"乃至"另一个产品"**。其中跨网远程是会话码+打洞+中继+Agent+账号的超集；无人值守 Agent 需 Windows/macOS/Linux/飞牛OS 四平台独立工程；其余各项分别要新建信令、中继、账号库、协议栈或画面管线。
2. **工作量量级存在数量级差异**：方案二里"自托管 RustDesk ID 服务器 + 外部调起"约 1–2 人周（主控端几乎不改）；"被控端 Agent + 仅局域网无人值守"约数人月；**方案三完整 C 类是多人月起步、需独立团队与持续 infra 投入——本质是另起一个创业项目**。
3. **推荐：方案一（维持现状）为默认；若用户确实要动 C 类，优先方案二的 2b（可选自托管 RustDesk ID 服务器），谨慎评估 2a（局域网无人值守 Agent）；不推荐方案三，除非用户明确要"做另一个产品"并接受重新立项、预算、团队与合规责任。**
4. 关键判断：**用户"一般远控功能我都需要"的诉求，大部分已由 B 类（mstsc / VNC Viewer / RustDesk 官方客户端）实际满足**；C 类里真正缺失且用户可感知的，主要是"无人值守"和"跨网/会话码"，而这两项恰恰代价最大。

## 一、评估方法与口径

### 1.1 评估维度（每项 C 类均按此六维打分）

| 维度 | 要回答的问题 |
|---|---|
| 技术可行性 | 在现有 Electron 主控端架构上加，还是必须新建组件？缺哪些基础设施？ |
| 工程量量级 | 人周/人月粗估；定性为"加功能"还是"新建子系统" |
| 许可与合规 | AGPL/GPL 传染、WebRTC/STUN/TURN、签名/公证/权限、隐私合规 |
| 运营成本 | 服务器/带宽/账号维护/多平台升级分发 |
| 安全风险 | 公网暴露面、账号与 Agent 提权、密钥管理、信任模型变化 |
| 架构冲突 | 推翻哪几条冻结口径（引用 `docs/02c` / `docs/11` 具体条目） |

### 1.2 量级定义（粗估，非排期承诺）

- **加功能**：在现有 Electron 三进程 + sql.js + 外部调起模型内可完成，不动产品定位。
- **新建子系统**：需新增独立服务端、常驻 Agent、账号库或协议栈，推翻至少一条冻结口径。
- **另一个产品级别**：需多团队、多平台Agent、公网 infra 与长期运营，接近独立立项。
- 人月按 4 人周折算。所有数字用于判断**量级差异**（数周 / 数月 / 跨月多人），**不作精确承诺**。

### 1.3 现有架构基线（来自 `docs/10`、`docs/02c`）

- 主控端：Electron 45 三进程（main/preload/renderer）+ 白名单 IPC；存储 sql.js（失败降级 JSON）。
- 连接模型：外部调起 `mstsc.exe` / VNC Viewer / RustDesk 官方客户端；主控端**不渲染画面、不自研协议栈、不录制视频流**（`docs/02c` §一.2）。
- 发现与凭据：端口扫描 3389/5900 + mDNS + 只读 ARP；凭据 safeStorage/DPAPI，`password 51:b:` 注入。
- 定位：纯局域网、无服务端、无公网中转、无账号、零遥测；被控端用现成开源服务、不自研被控端（`docs/02c` §一.1、§八；`README.md` 第二节）。

## 二、C 类 9 项逐项评估

### 2.1 会话码 / ID 连接（类似 RustDesk/ToDesk）

| 维度 | 评估 |
|---|---|
| 技术可行性 | 主控端侧只需"输入会话码 + 信令查询路由"的 UI/链路，**改造小**；但会话码体系的本体是**被控端向信令服务器注册 ID + 服务端路由**，必须新建信令（ID/rendezvous）服务与被控端注册逻辑。若走"外部调起 RustDesk 官方客户端 + 自托管 Server OSS"，主控端只需传 `rustdesk://<id>`，几乎不改代码——但这是"借外部能力"，不是自研会话码。 |
| 工程量量级 | 自研端到端会话码体系：**新建子系统**，信令服务 + Agent 注册 + 主控端接入，粗估 **2–4 人月起**；纯主控端 UI 接入外部 ID：约 **1–2 人周**（加功能）。 |
| 许可与合规 | 自研信令无特定传染；若采用 RustDesk Server OSS（AGPL-3.0）自托管，**运行未修改版本不触发 §13 源码义务**，但一旦修改并对外提供网络交互即触发；不得把 AGPL 代码嵌进主控端。 |
| 运营成本 | 信令服务需 7×24 可用性、域名、证书、监控；用户量上来后需扩容与备份。 |
| 安全风险 | 公网服务暴露；ID 猜测/撞库/未授权连接风险；信任模型由"仅连授权设备"变为"凭 ID+密码"，与现有合规声明冲突。 |
| 架构冲突 | 推翻 `docs/02c` §一.1"无服务端/无公网/无账号"、§八负向"公网中转/打洞、自研被控端"；`docs/11` §4"会话码/设备 ID 注册【明确不做】"；`README.md` 第二节负向清单。 |

### 2.2 P2P 打洞 + NAT 穿透

| 维度 | 评估 |
|---|---|
| 技术可行性 | 需 ICE/STUN/TURN 栈，主控端与被控端都要跑。Electron 主控端侧可用 WebRTC（`RTCPeerConnection`），但**被控端仍需 Agent**。**STUN 对对称 NAT 无效**：约 10–20% 连接需 TURN 兜底，企业严防火墙环境可达 25–40%（Cloudflare State of WebRTC 2025）。ICE/STUN/TURN 对应 RFC 8445 / 8489 / 8656。 |
| 工程量量级 | 接入现成 WebRTC 栈 + 信令：**新建子系统**，数人月；自研 ICE 协议：**另一个产品级别**，人月起。且 Electron `desktopCapturer` 配合 WebRTC 实测常跌到 5–6 fps、内存偏高，要达到可用帧率仍需 native 采集插件。 |
| 许可与合规 | libwebrtc/WebRTC 为 BSD 系，coturn 为 BSD，可直接用；但**大量现成 P2P 栈是 AGPL**，内嵌即触发传染义务——必须做 license 白名单审查。 |
| 运营成本 | STUN 极轻；TURN 是纯带宽中继，每字节走两遍，是主要成本项。 |
| 安全风险 | 打洞把内网设备暴露到公网可达路径；SDP 经信令交换，需 TLS 防中间人；增加可被扫描/探测的攻击面。 |
| 架构冲突 | 推翻 `docs/02c` §八负向"公网中转/打洞"；`docs/11` §4"P2P 打洞/NAT 穿透【明确不做】"；`docs/10` §2.2、§5 同一结论。 |

### 2.3 中继服务器（打洞失败兜底）

| 维度 | 评估 |
|---|---|
| 技术可行性 | 纯服务端组件（TURN/relay）+ 被控端 Agent 支持 relay。部署成熟方案（如 coturn）技术门槛不高；难点在容量、带宽与多地域。 |
| 工程量量级 | 部署开源 TURN：**新建子系统**，1–2 人周（不含运维）；自研高性能中继 + 调度：**数人月**。 |
| 许可与合规 | coturn 为 BSD；自研无传染。但若链路无端到端加密，**中继运营方成为事实中间人**，隐私责任重大。 |
| 运营成本 | 带宽是核心成本，TURN 流量 ×2；需监控、扩容、备份、证书轮换、地域节点。 |
| 安全风险 | 中继可见元数据乃至流量（除非 E2EE）；公网中继节点成为攻击与滥用目标；信任模型根本改变。 |
| 架构冲突 | 推翻 `docs/02c` §一.1"无服务端/无公网"、§八负向"公网中转"；`docs/11` §4"中继服务器/relay【明确不做】"及"端到端直连、无中转"定位（`docs/10` §2.1）。 |

### 2.4 账号体系 / 登录 / 2FA / 设备云同步

| 维度 | 评估 |
|---|---|
| 技术可行性 | 需用户库、认证服务、令牌体系、2FA（TOTP/短信/邮件）、设备数据托管与同步协议，以及隐私合规设计（PIPL/GDPR）。全新建后端 + 主控端登录 UI。 |
| 工程量量级 | **新建子系统**，认证服务 + DB + 2FA + 合规 + 运维，粗估 **3–6 人月起**；持续维护另计。 |
| 许可与合规 | 无特定 copyleft 传染，但密码学/身份依赖需选型审查；数据托管触发隐私合规义务。 |
| 运营成本 | 账号系统需长期维护、车辆级安全运维；用户数据托管责任（泄露通报、删除权、跨境）。 |
| 安全风险 | 攻击面大幅扩大：撞库、凭证填充、2FA 绕过、会话令牌窃取；密钥与密码存储成为高价值目标。 |
| 架构冲突 | 推翻 `docs/02c` §一.1"无账号"；`docs/11` §4"账号体系/登录/设备云同步【明确不做】""2FA【明确不做】"；`README.md` "无账号、不上传任何设备信息"。 |

### 2.5 无人值守访问（被控端常驻 Agent，Windows/macOS/Linux/飞牛OS 四平台）

| 维度 | 评估 |
|---|---|
| 技术可行性 | **必须新建被控端 Agent**，四平台各自独立：Windows 服务/自启、macOS LaunchAgent/LaunchDaemon + `Developer ID` 签名 + 公证 + Hardened Runtime + 屏幕录制(TCC)授权、Linux systemd + X11/Wayland 适配（Wayland 需 `xdg-desktop-portal`/PipeWire、输入走 uinput）、飞牛OS 基于定制 Linux 需单独适配。 |
| 工程量量级 | **另一个产品级别**：四个平台 Agent 各人月级，合计多人月到半年以上；另加签名/公证/自启/权限引导/自动升级。 |
| 许可与合规 | 自研 Agent 无传染但工作量极大；基于 RustDesk Agent 则为 AGPL-3.0。macOS 分发强制签名+公证（Apple Developer Program $99/年）；Windows 常驻/服务需 Authenticode 签名（OV/EV $200–700/年），2024-03 起 EV 不再即时绕过 SmartScreen，需累积信誉。 |
| 运营成本 | 多平台签名证书与公证流程、升级分发、OS 升级兼容性维护、被控端权限引导支持成本。 |
| 安全风险 | **最大暴露面**：常驻提权程序、自启持久化、被控端屏幕/输入/文件访问权限；一旦 Agent 被攻破或被伪装，风险直达系统层；需防篡改与安全更新机制。 |
| 架构冲突 | 推翻 `docs/02c` §一.1"被控端各平台现成开源 Agent"、§八负向"自研被控端"；`docs/10` §1.4"被控端用现成服务、不新装程序"；`docs/11` §4"无人值守/被控端常驻自启 Agent【明确不做】"；`README.md` 负向清单。 |

### 2.6 自研端到端加密

| 维度 | 评估 |
|---|---|
| 技术可行性 | "用通道自带的 E2EE"（RDP TLS、RustDesk 官方客户端 E2EE）属 B 类已具备；**"自研"是要自己造协议与密钥体系**：密钥协商（Noise/DTLS/双棘轮）、前向保密、密钥管理、跨平台实现与安全审计。 |
| 工程量量级 | **新建子系统**，密码学工程 + 审计，数人月起；自研密码学风险极高，行业惯例是"不要自己造密码"。 |
| 许可与合规 | 无特定 copyleft，但引入密码学依赖需审查；若与 AGPL 栈结合则触发传染。 |
| 运营成本 | 若涉及密钥/证书服务需持续运维；密钥轮换与泄露响应机制。 |
| 安全风险 | 密钥管理是核心难题，实现错误会导致"看似加密实则不安全"；信任模型从"通道提供"变为"自己承担全部密码学正确性"。 |
| 架构冲突 | 推翻 `docs/02c` §一.2"不自研协议栈"；`docs/11` §4"端到端加密（自研/宣称）【明确不做】"、§5"绝不宣称 VNC 已加密"的归属口径；`README.md` "不提供也不宣称提供 E2EE"。 |

### 2.7 自研文件传输通道（可断点续传）/ 常驻跨设备剪贴板

| 维度 | 评估 |
|---|---|
| 技术可行性 | 需自研传输协议、分片/断点续传状态、校验、加密与常驻进程；常驻剪贴板还需设备间同步通道（中心或 P2P）。现有用 SMB 资源管理器 / RDP 磁盘重定向；`robocopy /Z` 可改善但不承诺断点续传（`docs/11` §2、§6）。 |
| 工程量量级 | **新建子系统**：文件传输通道数人月；常驻剪贴板再加数人月（含保活与同步）。 |
| 许可与合规 | 无特定传染，但若引入 AGPL 传输库需注意；**常驻剪贴板会捕获密码/令牌等敏感内容，隐私合规风险极高**（需显式同意、加密、最小留存）。 |
| 运营成本 | 若走云中转有带宽成本；常驻进程需保活与跨设备状态维护。 |
| 安全风险 | 文件/剪贴板内容极度敏感；常驻剪贴板等于在后台持续采集用户剪切板，必须端到端加密与严格授权，否则成为数据泄露通道。 |
| 架构冲突 | 推翻 `docs/02c` §八负向"自研文件传输""常驻剪贴板"；`docs/10` §5、`docs/11` §4；`README.md` §九"LanDesk 不读取、不缓存、不上传其任何内容"。 |

### 2.8 跨网远程（脱离局域网）

| 维度 | 评估 |
|---|---|
| 技术可行性 | 不是单项能力，而是 **2.1+2.2+2.3+2.4+2.5 的超集**：要跨网就必须有信令、中继、被控端 Agent 与账号/权限体系；缺一不可。 |
| 工程量量级 | **另一个产品级别**：全部后端 + 四平台 Agent + 账号 + E2EE，多人月到跨年，需独立团队与持续 infra。 |
| 许可与合规 | 同时触发 AGPL/GPL 栈风险（若复用现成 P2P 栈）、多平台签名公证、数据跨境与隐私合规。 |
| 运营成本 | 公网服务器 + 中继带宽 + 账号系统 + 多平台升级分发，全面新增。 |
| 安全风险 | 暴露面从"局域网内"跃迁到"公网可达"，账号/Agent/中继三线受攻击，信任模型彻底改变。 |
| 架构冲突 | 推翻**几乎所有冻结口径**：`docs/02c` §一.1"纯局域网、无服务端、无公网"、§八负向全部相关项；`docs/11` §0/§4 根基论述；`README.md` 标题与定位。 |

### 2.9 会话录像 / 屏幕录制

| 维度 | 评估 |
|---|---|
| 技术可行性 | 主控端"不渲染画面、不录制视频流"（`docs/02c` §一.2），要录像必须**接管画面层**。Electron `desktopCapturer` 性能低（实测 5–6 fps、内存高），要达可用质量需 native 采集（Windows DXGI/GDI）+ 编码管线。 |
| 工程量量级 | **新建子系统**：画面管线 + 录制/编码/存储 + 权限告知，数人月起；且要改"调起即失焦"的会话模型。 |
| 许可与合规 | 编码库需注意（x264 为 GPL、OpenH264 为 BSD）；**录像含密码输入与隐私界面，告知同意与被控端知情权是硬合规门槛**，存储加密与访问控制必需。 |
| 运营成本 | 录像存储成本（本地或云）；若云端存储则合规责任陡增。 |
| 安全风险 | 录像文件是高价值敏感数据；泄露、误存、未授权回放风险大；需端到端加密与严格权限。 |
| 架构冲突 | 推翻 `docs/02c` §一.2"不录制视频流"、§八负向"画面录制"；`docs/11` §4"会话时长/码率/帧率统计【明确不做】"；`README.md` 负向清单。 |

| 7 | 自研文件传输/常驻剪贴板 | 新建子系统 | 数人月 | 传输通道 + 常驻进程 | 剪贴板隐私、内容加密 | 多 |
| 8 | 跨网远程 | 另一个产品级别 | 多人月～跨年 | 1+2+3+4+5 全部 | 全部叠加 | 几乎全部 |
| 9 | 会话录像 | 新建子系统 | 数人月 | 画面管线 + 编码/存储 | 录像隐私/知情同意、编码库 GPL | 中 |

> 读表：除第 1 项的"外部 ID 借力"路径外，**没有一项是"加功能"级别**。这就是为什么 C 类整体被定性为"另一个工程量级"。

## 四、方案对比

### 方案一：维持现状（只做 A+B 类本地编排，C 类全部不做）

| 项目 | 内容 |
|---|---|
| 范围 | 继续 v1.6/v1.7 的 A 类（收藏/别名/分组、搜索排序、导入导出、会话备注、连接预设、在线状态刷新等，见 `docs/16` §二）+ B 类最大化（选对客户端、传对参数、给对指引）；C 类 9 项全不做。 |
| 工程量 | C 类为 **0**；A+B 类为现有架构内的增量迭代（人周级/项）。 |
| 代价 | C 类诉求未被满足；"一般远控功能我都需要"里的无人值守、跨网、会话码仍需用户另装 ToDesk/RustDesk 等解决。 |
| 收益 | 保持零服务端、零遥测、MIT、无 AGPL/GPL 传染、无公网暴露面、轻量；冻结口径不动，风险最低。 |
| 风险 | 主要风险是"用户期待落差"，可通过 B 类体验最大化 + 清晰的能力边界说明缓解；无技术/合规/运营新增风险。 |

### 方案二：渐进混合（保留局域网编排器定位，只挑 1–2 项 C 类做）

提供两个低耦合切入点，**按需选其一，其余 C 类仍不做**：

#### 2a：被控端 Agent + 仅局域网无人值守（不碰公网/信令/中继/账号）

| 项目 | 内容 |
|---|---|
| 范围 | 在局域网内自研一个常驻 Agent，实现"设备开机自启、无需用户在被控端点击即可连接"；Agent **只监听局域网、不连公网、不注册 ID、不要账号**。P2P 打洞、中继、跨网、账号、E2EE、文件/剪贴板、录像仍不做。 |
| 工程量 | **数人月**（Agent + 四平台自启/权限/签名/升级；若先只做 Windows 单平台约 1–2 人月）。 |
| 代价 | 引入被控端常驻程序与签名成本；必须修订"不新装程序/不自研被控端"冻结口径；用户被控端要安装并授权 Agent。 |
| 收益 | 补齐"无人值守"这一最常被感知的缺口；仍守住无服务端、零遥测、无账号。 |
| 风险 | Agent 提权/自启是新的安全暴露面；多平台兼容性维护；若做四平台则接近方案三的 Agent 工作量。 |

#### 2b：可选自托管 RustDesk ID 服务器 + 外部调起（推荐切入点）

| 项目 | 内容 |
|---|---|
| 范围 | 主控端不改架构：增加"会话码/ID 连接"入口，按 `rustdesk://<id>` 外部调起**独立安装的官方客户端**；提供一份"如何用 Docker 自托管 RustDesk Server OSS（ID/relay）"的可选配置指引。**不内嵌、不捆绑、不修改**任何 AGPL 代码。其余 C 类仍不做。 |
| 工程量 | **1–2 人周**（主控端 UI/参数 + 文档；服务端部署由用户自行完成，不在 LanDesk 内）。 |
| 代价 | 会话码/打洞/中继能力实际由 RustDesk 官方客户端与其服务端提供，LanDesk 只做入口；用户需自备服务器与带宽。 |
| 收益 | 以极小代价满足"会话码/跨网连接"的表面诉求；守住主控端零服务端、零遥测、MIT 架构；运行未修改的 Server OSS 不触发 AGPL §13 源码义务。 |
| 风险 | 需清晰披露"这是外部 RustDesk 能力，不是 LanDesk 自研/宣称"；若将来修改 Server OSS 则触发 AGPL 义务；用户自建服务器的安全由用户承担。 |

> 方案二明确**仍不做**：自研 P2P 栈、自研中继、账号/2FA、自研 E2EE、自研文件/剪贴板通道、跨网自研、会话录像。

### 方案三：全栈重做（完整 C 类，成为与 ToDesk/RustDesk 同类产品）

| 项目 | 内容 |
|---|---|
| 范围 | 完整实现 C 类 9 项：会话码 + P2P 打洞 + 中继 + 账号/2FA/云同步 + 四平台常驻 Agent + 自研 E2EE + 自研文件/剪贴板 + 跨网 + 会话录像；成为端到端全栈远控。 |
| 工程量 | **另一个产品级别**：后端三件套（信令/中继/账号）+ 四平台 Agent + E2EE + 文件/剪贴板 + 录像，多人月到跨年，需独立团队、长期 infra 预算与专职安全/合规。 |
| 代价 | 推翻全部冻结口径；MIT 自研部分会被 AGPL/GPL 依赖与公网服务运营包围；从"零服务端零遥测"变成重资产 SaaS/服务；承担数据托管与隐私责任。 |
| 收益 | 功能可对标商业远控，形成完整自主产品。 |
| 风险 | **极高且叠加**：工程量失控、许可传染、公网攻击面、账号/Agent/中继三线安全、录像与剪贴板隐私合规、运营成本持续化。这是"重新创业"，不是在现有项目上加版本。 |

### 4.4 方案对比矩阵

| 维度 | 方案一 维持现状 | 方案二 渐进混合 | 方案三 全栈重做 |
|---|---|---|---|
| 是否改变定位 | 否 | 否（2a/2b 均保留编排器定位，仅局部） | 是（彻底重定义） |
| C 类覆盖 | 0/9 | 1–2/9（2a 或 2b） | 9/9 |
| 工程量 | 0 | 1–2 人周(2b) / 数人月(2a) | 多人月～跨年 |
| 新基础设施 | 无 | 2b 无（用户自建）/ 2a 仅 Agent | 信令+中继+账号+Agent+E2EE |
| 许可风险 | 无 | 低（2b 不修改 AGPL 代码） | 高 |
| 运营成本 | 无 | 低 | 高且持续 |
| 安全暴露面 | 局域网内 | 小（2a 增 Agent） | 公网全面暴露 |
| 冻结文档改动 | 无 | 需小改 `docs/16`/`11`/`README` | 全部重写 |
| 满足"全都要"诉求 | 否 | 部分 | 是 |

## 五、明确推荐

**推荐方案一为默认；若用户决定动 C 类，走方案二的 2b（自托管 RustDesk ID 服务器 + 外部调起），谨慎评估 2a；不推荐方案三。**

理由：

1. **量级现实**：C 类 9 项中 8 项是新建子系统或另一个产品；把它们塞进"v1.6 加功能"是不诚实的。只有 2b 是真正的小改动。
2. **诉求错位**：用户"一般远控功能我都需要"的大部分（画面、键鼠、剪贴板、文件传输、全屏、多显示器）已由 B 类外部客户端提供；真正缺的无人值守/跨网恰恰代价最大，先做 2b 可用极低成本覆盖"会话码/跨网"的表面需求。
3. **风险不对称**：方案一/2b 几乎不增加新的安全、合规与运营责任；方案三把项目从轻量工具变成重资产服务，风险与成本呈数量级上升。
4. **可逆性**：2b 是可选、可撤回的入口；方案三一旦投入不可轻易回头。

> 若用户的核心诉求具体就是"无人值守"（例如需要远程维护不在场、无人点击的机器），则优先讨论 **2a 且先只做 Windows 单平台**（约 1–2 人月），验证价值后再决定是否扩平台——**不要一上来就做四平台**。

## 七、若决定做方案二 / 三：先修订哪些文档、先做哪些前置决策

### 7.1 方案二前置项

**必须先修订的文档：**

4. `README.md` 第二节负向清单与定位描述：同步删改对应项，并补充"外部 RustDesk 能力非自研"的披露（2b）。
5. `RELEASE_NOTES.md`：在对应版本明确列出交付项（与 `docs/16` §六口径一致）。

**必须先做的前置决策：**
- 选 2a 还是 2b（还是两者都做，但注意 2a 若做四平台已接近方案三 Agent 工程量）。

- 2b：是否接受"能力由外部客户端提供"的披露口径；是否为将来修改 Server OSS 预留法务审查。

### 7.2 方案三前置项

**必须先修订的文档（全部重写级别）：**
- `docs/02c`（整体重定义验收标准）、`docs/02` PRD、`docs/11`（负向清单大幅删改）、`docs/10`（架构从"外部调起"改为"自研全栈"）、`README.md`（定位、许可、隐私整节重写）、`docs/16`（C 类不再默认不做）。

**必须先做的前置决策（立项级）：**
1. 商业模式与预算：公网 infra 预算、带宽预估、团队规模（后端/客户端/四平台 Agent/安全/合规）。
2. 平台优先级：先做哪几个被控端平台，是否真需要四平台同时上线。
3. 协议栈选型：自研 vs 复用 AGPL 栈（决定 MIT 能否保留、是否触发传染）。
4. 基础设施选型：信令/中继（自研 vs coturn vs 商用 TURN）、账号体系、存储与数据托管地。
5. 合规负责人与法律审查：AGPL/GPL 合规、PIPL/GDPR、录像与剪贴板的知情同意与数据留存策略。
6. 安全设计评审：公网暴露面、Agent 提权与防篡改、E2EE 密钥管理、账号与 2FA 安全。

> 在这些决策完成前，**不应把任何 C 类能力写进实现清单或版本计划**。
